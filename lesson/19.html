Tổng quan về RESTful API

1.1. API là gì?

API là viết tắt của Application Programming Interface, nghĩa là giao diện lập trình ứng dụng.

API cung cấp một cách thức để các thành phần phần mềm giao tiếp và sử dụng chức năng hoặc dữ liệu của nhau mà không cần biết toàn bộ cách triển khai bên trong.

Hãy xét ví dụ một ứng dụng quản lý sản phẩm.

Frontend cần hiển thị danh sách sản phẩm nhưng không trực tiếp truy cập vào mã nguồn xử lý bên trong Backend. Thay vào đó, Frontend gửi yêu cầu đến API mà Backend cung cấp.

Frontend
Giao diện người dùng
        |
        v
API
Tiếp nhận yêu cầu và cung cấp dữ liệu
        |
        v
Backend
Xử lý yêu cầu và thực hiện nghiệp vụ

Ví dụ, Frontend muốn lấy danh sách sản phẩm, Backend cung cấp một API có địa chỉ:

HTTP
GET /api/products

Khi nhận yêu cầu này, Backend xử lý và trả về dữ liệu:

JSON
[
  {
    "id": 1,
    "name": "Laptop Dell",
    "price": 15000000
  },
  {
    "id": 2,
    "name": "Laptop HP",
    "price": 18000000
  }
]

Frontend nhận dữ liệu JSON và sử dụng dữ liệu đó để hiển thị thành danh sách sản phẩm trên giao diện.

Điểm cần nhớ

API là giao diện giao tiếp giữa các thành phần phần mềm. API không đồng nghĩa với Database, cũng không phải toàn bộ ứng dụng Backend.

1.2. Web API là gì?

Web API là API được cung cấp thông qua các công nghệ web, thường sử dụng giao thức HTTP hoặc HTTPS để giao tiếp.

Ví dụ, một ứng dụng Spring Boot cung cấp địa chỉ:

HTTP
http://localhost:8080/api/products

Trong đó:

  • http là giao thức giao tiếp.
  • localhost là máy đang chạy ứng dụng.
  • 8080 là cổng ứng dụng.
  • /api/products là đường dẫn đến tài nguyên mà API cung cấp.

Khi Frontend gửi HTTP Request đến địa chỉ này, ứng dụng Spring Boot có thể tiếp nhận yêu cầu, xử lý và trả về HTTP Response.

Web API có thể được xây dựng bằng nhiều công nghệ khác nhau, chẳng hạn Spring Boot, ASP.NET Core, Node.js hoặc Django.

Trong khóa học này, chúng ta sử dụng Java và Spring Boot để xây dựng Web API.

1.3. REST là gì?

REST là viết tắt của Representational State Transfer. Đây là một kiểu kiến trúc dùng để thiết kế các hệ thống phân tán, đặc biệt phổ biến trong xây dựng Web API.

REST định hướng cách thiết kế API thông qua các tài nguyên, cách định danh tài nguyên và cách sử dụng những quy ước giao tiếp của HTTP.

Để hiểu REST, trước tiên cần hiểu khái niệm Resource — tài nguyên.

Trong ứng dụng quản lý bán hàng, tài nguyên có thể là:

Tài nguyên Ý nghĩa
ProductsDanh sách sản phẩm
ProductMột sản phẩm cụ thể
CategoriesDanh sách danh mục
CustomersDanh sách khách hàng
OrdersDanh sách đơn hàng

Mỗi tài nguyên thường được xác định bằng một URI.

Ví dụ:

URI
/api/products
/api/products/1
/api/categories
/api/customers
/api/orders

Trong đó:

  • /api/products đại diện cho tập hợp sản phẩm.
  • /api/products/1 đại diện cho sản phẩm có mã định danh 1.
  • /api/categories đại diện cho tập hợp danh mục.

REST khuyến khích thiết kế địa chỉ dựa trên tài nguyên thay vì đặt tên URL theo hành động.

Ví dụ:

HTTP
GET /api/products
POST /api/products
GET /api/products/1
DELETE /api/products/1

Các URL trên đều hướng đến tài nguyên sản phẩm. Ý nghĩa của thao tác được xác định bởi HTTP Method.

Ngược lại, cách thiết kế như sau thường không được ưu tiên:

HTTP
/getAllProducts
/createProduct
/deleteProductById/1

Lý do là hành động đã được thể hiện thông qua HTTP Method nên không cần lặp lại hành động trong tên URL.

1.4. RESTful API là gì?

RESTful API là Web API được thiết kế theo các nguyên tắc và ràng buộc của kiến trúc REST.

Trong thực tế, thuật ngữ này thường được sử dụng để chỉ các API sử dụng tài nguyên, URI rõ ràng, HTTP Method phù hợp và HTTP Status Code có ý nghĩa.

Ví dụ với tài nguyên sản phẩm:

HTTP Method Endpoint Ý nghĩa
GET/api/productsLấy danh sách sản phẩm
GET/api/products/1Lấy sản phẩm có ID bằng 1
POST/api/productsTạo sản phẩm mới
PUT/api/products/1Cập nhật toàn bộ thông tin sản phẩm
PATCH/api/products/1Cập nhật một phần thông tin sản phẩm
DELETE/api/products/1Xóa sản phẩm có ID bằng 1

Bảng trên thể hiện cách thiết kế API theo tài nguyên. Ở các phần tiếp theo, chúng ta sẽ thực hành từng loại Request bằng Spring Boot.

Cần lưu ý rằng một API không tự động trở thành RESTful chỉ vì sử dụng HTTP và trả về JSON. REST có những ràng buộc kiến trúc rộng hơn, trong đó có Client–Server, Stateless, Cacheable, Uniform Interface và Layered System. Trong một số định nghĩa đầy đủ, Code-on-Demand là ràng buộc tùy chọn.

1.5. Phân biệt API, REST và RESTful API

Ba khái niệm này có liên quan nhưng không giống nhau.

Khái niệm Ý nghĩa
APIGiao diện để các thành phần phần mềm giao tiếp
Web APIAPI giao tiếp qua công nghệ web, thường dùng HTTP/HTTPS
RESTKiểu kiến trúc với các nguyên tắc và ràng buộc thiết kế
RESTful APIWeb API được thiết kế theo kiến trúc REST

Ví dụ, một ứng dụng Spring Boot có thể cung cấp API qua HTTP nhưng thiết kế Endpoint không theo nguyên tắc tài nguyên của REST. Đó vẫn có thể là Web API, nhưng chưa chắc là RESTful API theo nghĩa chặt chẽ.

1.6. Client và Server trong RESTful API

Trong mô hình giao tiếp HTTP, Client là bên gửi yêu cầu và Server là bên tiếp nhận, xử lý yêu cầu đó.

Client có thể là:

  • Website được xây dựng bằng HTML, CSS và JavaScript.
  • Ứng dụng React hoặc Angular.
  • Ứng dụng di động Android hoặc iOS.
  • Postman được sử dụng để kiểm thử API.
  • Một Backend khác cần gọi đến API.

Server là hệ thống cung cấp API, thực hiện xử lý và trả về kết quả.

Trong khóa học này, Spring Boot đóng vai trò xây dựng ứng dụng Server.

Ví dụ về luồng giao tiếp:

Người dùng
    |
    v
Frontend (React)
    |
    | HTTP Request
    v
Spring Boot Backend
    |
    | Xử lý yêu cầu
    v
HTTP Response (JSON)
    |
    v
Frontend hiển thị kết quả

Ở giai đoạn đầu, chúng ta chưa cần kết nối Database. Backend có thể trả về dữ liệu mẫu được khai báo trực tiếp trong Java để tập trung hiểu cơ chế hoạt động của API.

1.7. Quy trình hoạt động của một RESTful API

Giả sử người dùng mở trang danh sách sản phẩm.

Bước 1: Frontend gửi Request đến Backend:

HTTP
GET /api/products

Bước 2: Spring Boot tiếp nhận Request và xác định Controller phù hợp.

Bước 3: Controller thực hiện xử lý cần thiết. Trong bài học này, dữ liệu có thể được lấy từ một danh sách mẫu trong bộ nhớ.

Bước 4: Spring Boot chuyển đổi dữ liệu Java thành JSON và tạo HTTP Response.

Bước 5: Frontend nhận JSON và hiển thị danh sách sản phẩm.

Ví dụ Response:

HTTP

Content-Type: application/json
JSON
[
  {
    "id": 1,
    "name": "Laptop Dell",
    "price": 15000000
  }
]

Có thể tóm tắt quy trình như sau:

1. Client gửi HTTP Request
        |
        v
2. Spring Boot tiếp nhận Request
        |
        v

        |
        v

        |

1.8. Vai trò của Spring Boot khi xây dựng RESTful API

Spring Boot giúp xây dựng ứng dụng Backend bằng Java với cấu hình thuận tiện và khả năng tích hợp hệ sinh thái Spring.

Khi xây dựng RESTful API, chúng ta thường sử dụng Spring Web, dựa trên Spring MVC, để xử lý HTTP Request và HTTP Response.

Spring Boot hỗ trợ:

  • Khởi tạo và chạy ứng dụng web.
  • Tiếp nhận HTTP Request.
  • Ánh xạ Request đến Controller.
  • Nhận dữ liệu từ URL, Query Parameter và Request Body.
  • Chuyển đổi dữ liệu Java thành JSON.
  • Trả về HTTP Status Code và Response Header.
  • Tích hợp các thành phần khác khi dự án phát triển.

Trong phần đầu của khóa học, chúng ta chỉ sử dụng Spring Web và Controller. Các thành phần như Database, JPA, Service và Repository sẽ được học ở những bài sau.

Ánh xạ URL và HTTP Method

Trong phần 1, chúng ta đã tìm hiểu RESTful API là gì, Client giao tiếp với Server như thế nào và vai trò của Spring Boot trong việc xây dựng API.

Ở phần này, chúng ta bắt đầu làm quen với cơ chế ánh xạ URL và HTTP Method trong Spring MVC. Nội dung tập trung vào @RequestMapping, cách Spring Boot xác định Endpoint và cách kết hợp đường dẫn ở cấp Class với cấp Method.

Chi tiết cách sử dụng từng HTTP Method như GET, POST, PUT, PATCH, DELETE sẽ được trình bày ở các phần học riêng.

1. Khái niệm ánh xạ URL

Ánh xạ URL (URL Mapping) là cơ chế xác định phương thức xử lý tương ứng khi ứng dụng Spring Boot nhận được một HTTP Request.

Ví dụ, khi Client gửi yêu cầu đến:

HTTP
GET /api/products

Spring MVC sẽ tìm Controller và phương thức có cấu hình ánh xạ phù hợp để xử lý yêu cầu này.

Quy trình tổng quát:

Client gửi HTTP Request
          |
          v
   DispatcherServlet
          |
          v
 Tìm Handler phù hợp
          |
          v
   Controller Method
          |
          v
    Trả về Response

2. Sử dụng @RequestMapping

@RequestMapping là annotation dùng để khai báo quy tắc ánh xạ Request đến Controller hoặc phương thức xử lý.

Ví dụ:

Java
@RestController
@RequestMapping("/api/products")
public class ProductController {

    @RequestMapping("/hello")
    public String hello() {
        return "Hello Product API";
    }
}

Trong ví dụ trên:

  • @RestController: đánh dấu lớp xử lý HTTP Request và trả dữ liệu trực tiếp về Response Body.
  • @RequestMapping("/api/products"): khai báo đường dẫn chung cho Controller.
  • @RequestMapping("/hello"): khai báo đường dẫn của phương thức.

Spring kết hợp hai đường dẫn để tạo thành Endpoint:

/api/products + /hello
          |
          v
/api/products/hello

Client có thể gửi Request đến:

HTTP
http://localhost:8080/api/products/hello

3. Ánh xạ ở cấp Class và cấp Method

Trong Spring MVC, có thể khai báo ánh xạ tại hai cấp.

Ánh xạ cấp Class

Xác định đường dẫn chung cho một nhóm API.

Java
@RestController
@RequestMapping("/api/products")
public class ProductController {
}

Ánh xạ cấp Method

Xác định đường dẫn cụ thể cho từng phương thức xử lý.

Java
@GetMapping
public String getProducts() {
    return "Danh sach san pham";
}

@GetMapping("/hello")
public String hello() {
    return "Hello";
}

Các Endpoint tương ứng:

Đường dẫn Chức năng minh họa
/api/productsLấy danh sách sản phẩm
/api/products/helloTrả về thông báo

Việc đặt đường dẫn chung ở cấp Class giúp hạn chế lặp lại URL và làm cho cấu trúc API dễ quản lý hơn.

4. Mối quan hệ giữa URL và HTTP Method

Khi xác định một Request có khớp với phương thức xử lý hay không, Spring MVC xem xét URL cùng các điều kiện ánh xạ, trong đó có HTTP Method.

Ví dụ, hai Request sau có cùng URL nhưng khác HTTP Method:

HTTP
GET /api/products
POST /api/products

Chúng có thể được ánh xạ đến hai phương thức Controller khác nhau.

Spring Boot cung cấp các annotation chuyên biệt:

Annotation HTTP Method
@GetMappingGET
@PostMappingPOST
@PutMappingPUT
@PatchMappingPATCH
@DeleteMappingDELETE

Các annotation này là dạng rút gọn của @RequestMapping, giúp khai báo HTTP Method rõ ràng hơn.

Chi tiết cách sử dụng từng HTTP Method sẽ được trình bày ở phần học tương ứng.

5. Một số lưu ý khi ánh xạ URL

  • URL phải được khai báo nhất quán giữa cấp Class và cấp Method.
  • Hai phương thức không nên có cấu hình ánh xạ trùng nhau gây xung đột.
  • Nên sử dụng tên tài nguyên rõ ràng, chẳng hạn /api/products, thay vì đặt URL theo tên hành động như /getAllProducts.
  • Khi Request không khớp với Endpoint phù hợp, Spring MVC có thể trả về lỗi HTTP tương ứng, thường gặp là 404 Not Found hoặc 405 Method Not Allowed, tùy tình huống.

6. Tổng kết

  • Khái niệm URL Mapping trong Spring MVC.
  • Vai trò của @RequestMapping.
  • Cách kết hợp ánh xạ cấp Class và cấp Method.
  • Mối quan hệ giữa URL và HTTP Method.
  • Các annotation ánh xạ HTTP Method thường dùng.
Ghi nhớ trọng tâm
  • Ánh xạ URL là cơ chế xác định phương thức xử lý tương ứng khi Spring Boot nhận HTTP Request.
  • @RequestMapping có thể đặt trên Class (đường dẫn chung) và trên Method (đường dẫn cụ thể); Spring kết hợp cả hai để tạo Endpoint.
  • Đặt đường dẫn chung ở cấp Class giúp hạn chế lặp lại URL và dễ quản lý cấu trúc API.
  • URL xác định tài nguyên, HTTP Method xác định thao tác — cùng URL có thể ánh xạ đến nhiều phương thức khác nhau tùy HTTP Method.
  • @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping là dạng rút gọn của @RequestMapping, giúp khai báo HTTP Method rõ ràng hơn.
  • Nên đặt URL theo tên tài nguyên (/api/products) thay vì theo hành động (/getAllProducts).
  • Request không khớp Endpoint thường trả về 404 Not Found hoặc 405 Method Not Allowed.
  • Chi tiết từng HTTP Method và cách xử lý dữ liệu vào/ra sẽ được học ở các phần tiếp theo.

1. Model là gì?

Model là class đại diện cho một đối tượng trong thực tế (User, Product, Employee...). Nó định nghĩa cấu trúc dữ liệu mà ứng dụng sẽ sử dụng.

Ví dụ:

  • Người dùng thực tế: Nguyễn Văn A, 25 tuổi, email a@gmail.com
  • Trong code: User object có các thuộc tính: id, name, age, email

@GETMAPPING - XỬ LÝ GET REQUEST

1. Định nghĩa

@GetMapping là một annotation trong Spring Framework dùng để ánh xạ (map) các HTTP GET request đến các handler method cụ thể trong controller. Đây là một composed annotation — viết tắt của @RequestMapping(method = RequestMethod.GET).

GET là phương thức dùng để lấy dữ liệu từ server.

2. Mục đích sử dụng

  • Lấy danh sách tất cả users
  • Lấy chi tiết một user theo ID
  • Tìm kiếm users theo điều kiện
  • Không làm thay đổi dữ liệu trên server

3. Cú pháp cơ bản

Cú pháp
@GetMapping("/duong-dan")
public KieuTraVe tenHam() {
    // Xử lý logic
    return duLieu;
}

KieuTraVe Kiểu dữ liệu trả về List<User>, String, User
tenHam() Tên hàm xử lý getAllUsers()
return duLieu; Dữ liệu trả về cho client return users;

UserController.java
package com.example.demo.controller;

import com.example.demo.model.User;
import org.springframework.web.bind.annotation.*;

import java.util.ArrayList;
import java.util.List;

@RestController
@RequestMapping("/user")
public class UserController {

    // 1. Tạo List lưu trữ users
    private List<User> users = new ArrayList<>();

    // 2. Constructor khởi tạo dữ liệu mẫu
    public UserController() {
        users.add(new User("1", "Nguyen Van A", "a@gmail.com", "123456"));
        users.add(new User("2", "Tran Thi B", "b@gmail.com", "789012"));
        System.out.println("Đã khởi tạo " + users.size() + " user mẫu");
    }

    // 3. GET - Lấy tất cả users
    @GetMapping("/getAll")
    public List<User> getAllUsers() {
        return users;
    }

    // 4. GET - Lấy user theo ID (dùng PathVariable)
    @GetMapping("/getUser/{id}")
    public String getUserById(@PathVariable String id) {
        for (User user : users) {
            if (user.getId().equals(id)) {
                return "Tìm thấy: " + user.getName();
            }
        }
        return "Không tìm thấy user ID: " + id;
    }

    // 5. GET - Tìm kiếm user theo tên (dùng RequestParam)
    @GetMapping("/search")
    public String searchUser(@RequestParam String name) {
        List<String> foundUsers = new ArrayList<>();
        for (User user : users) {
            if (user.getName().toLowerCase().contains(name.toLowerCase())) {
                foundUsers.add(user.getName());
            }
        }

        if (foundUsers.isEmpty()) {
            return "Không tìm thấy user nào có tên chứa: " + name;
        }
        return "Tìm thấy: " + String.join(", ", foundUsers);
    }

    // 6. POST - Thêm user mới
    @PostMapping("/addUser")
    public String addUser(@RequestBody User user) {
        users.add(user);
        return "Đã thêm user: " + user.getName() + ", tổng số: " + users.size();
    }

    // 7. DELETE - Xóa user theo ID
    @DeleteMapping("/deleteUser/{id}")
    public String deleteUser(@PathVariable String id) {
        boolean removed = users.removeIf(user -> user.getId().equals(id));

        if (removed) {
            return "Đã xóa user ID: " + id + ", còn lại: " + users.size() + " user";
        } else {
            return "Không tìm thấy user ID: " + id;
        }
    }

    // 8. GET - Lấy tổng số user
    @GetMapping("/count")
    public String getCount() {
        return "Tổng số user: " + users.size();
    }
}

3 @RequestParam Lấy tham số từ query string ?key=value
4 @PathVariable Lấy tham số từ URL /{id}
5 @PostMapping Xử lý POST request - thêm dữ liệu
6 @RequestBody Nhận JSON từ client, chuyển thành object
7 @DeleteMapping Xử lý DELETE request - xóa dữ liệu
8 List Lưu trữ dữ liệu tạm thời
