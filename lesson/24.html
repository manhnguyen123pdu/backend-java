Service Layer & Business Logic trong Java Spring

Bài học giúp bạn hiểu sâu tầng Service — "bộ não" của ứng dụng Spring Boot: nơi tập trung toàn bộ quy tắc nghiệp vụ, điều phối dữ liệu và quản lý transaction.

🎯 Mục tiêu học tập

  • Hiểu vai trò và trách nhiệm của Service Layer trong kiến trúc ứng dụng Spring.
  • Phân biệt rạch ròi trách nhiệm giữa Controller — Service — Repository.
  • Biết cách đặt Business Logic đúng chỗ, tránh "fat controller" và "anemic domain".
  • Nắm vững @Service, Dependency Injection và @Transactional.
  • Viết được Service Layer có thể kiểm thử (unit test) độc lập.
  • Nhận diện và tránh các anti-pattern phổ biến.
💡
Định vị bài học: Đây là bài trọng tâm trong chuỗi Backend Java Spring, nối tiếp bài Spring Boot Fundamentals và REST API với Controller, làm nền tảng cho các bài JPA/Hibernate, Transaction và Security.

2 Kiến trúc phân lớp (Layered Architecture)

Ứng dụng Spring Boot tiêu chuẩn được tổ chức thành các tầng, mỗi tầng chỉ giao tiếp với tầng liền kề. Luồng xử lý một request đi từ ngoài vào trong:

🌐 Controller Layer
Tiếp nhận HTTP request · Validate input · Gọi Service · Trả về Response
↓
⚙️ Service Layer
Business Logic · Điều phối nhiều Repository · Transaction Boundary
↓
🗄️ Repository Layer
Truy vấn dữ liệu · Ánh xạ Entity · Không chứa nghiệp vụ
↓
💾 Database
MySQL · PostgreSQL · MongoDB · …

Bảng phân chia trách nhiệm

TầngTrách nhiệm chínhKHÔNG nên làm
Controller Nhận request, validate dữ liệu đầu vào, gọi Service, trả HTTP response Không viết business logic, không gọi Repository trực tiếp
Service Chứa toàn bộ quy tắc nghiệp vụ, điều phối Repository, quản lý transaction, mapping DTO Không biết gì về HTTP (HttpServletRequest, ResponseEntity…)
Repository Truy vấn và thao tác dữ liệu (CRUD), định nghĩa query Không chứa if/else nghiệp vụ, không gọi Service
⚠️
Nguyên tắc một chiều: Controller → Service → Repository. Không bao giờ để Repository gọi ngược lên Service, hay Controller gọi thẳng Repository (trừ vài trường hợp CRUD cực đơn giản ở dự án nhỏ).

3 Service Layer là gì?

Service Layer là tầng trung gian nằm giữa Controller và Repository, đóng vai trò điều phối (orchestration) và hiện thực hóa nghiệp vụ của hệ thống.

🧠

Chứa Business Rules

Toàn bộ quy tắc nghiệp vụ: kiểm tra điều kiện, tính toán, áp dụng chính sách.

🔗

Điều phối dữ liệu

Gọi nhiều Repository khác nhau và tổng hợp kết quả thành một luồng xử lý thống nhất.

🛡️

Transaction Boundary

Xác định phạm vi transaction: hoặc tất cả thành công, hoặc rollback toàn bộ.

🔄

Entity ↔ DTO

Chuyển đổi giữa Entity (tầng DB) và DTO (tầng API) để bảo vệ dữ liệu nội bộ.

🚨

Ném Exception nghiệp vụ

Ném ra BusinessException khi vi phạm quy tắc, để tầng trên xử lý.

♻️

Tái sử dụng

Cùng một logic dùng được cho REST API, scheduled job, message consumer…

Interface + Implementation — có cần thiết?

Trong các dự án lớn, người ta thường tách OrderService (interface) và OrderServiceImpl. Điều này giúp:

  • Dễ mock khi viết unit test cho tầng Controller.
  • Cho phép nhiều implementation (ví dụ: VnPayPaymentService, MomoPaymentService).
  • Tuân thủ nguyên lý Dependency Inversion (chữ D trong SOLID).
💡
Với dự án nhỏ hoặc CRUD đơn giản, dùng class trực tiếp với @Service là hoàn toàn chấp nhận được — đừng over-engineer.

4 Business Logic nên đặt ở đâu?

Hãy xét một nghiệp vụ thực tế: Khách hàng đặt hàng. Luồng xử lý gồm:

  1. Kiểm tra giỏ hàng không rỗng
  2. Kiểm tra từng sản phẩm còn tồn kho
  3. Tính tổng tiền
  4. Áp mã voucher nếu có
  5. Trừ số lượng tồn kho
  6. Tạo đơn hàng ở trạng thái PENDING
  7. Gửi email xác nhận

Tất cả 7 bước trên đều thuộc Service Layer. Controller chỉ nên làm đúng một việc: nhận request và gọi orderService.createOrder(...).

❌ Anti-pattern: Fat Controller

OrderController.java — SAI 
@PostMapping("/orders")
public ResponseEntity<?> create(@RequestBody CreateOrderRequest req) {
    // ❌ Controller đang gánh toàn bộ business logic
    if (req.getItems().isEmpty()) {
        return ResponseEntity.badRequest().body("Giỏ hàng rỗng");
    }
    BigDecimal total = BigDecimal.ZERO;
    for (var i : req.getItems()) {
        Product p = productRepository.findById(i.getProductId()).get();
        if (p.getStock() < i.getQuantity()) {
            return ResponseEntity.badRequest().body("Hết hàng");
        }
        total = total.add(p.getPrice().multiply(BigDecimal.valueOf(i.getQuantity())));
    }
    Order order = new Order();
    order.setTotal(total);
    orderRepository.save(order);
    emailService.send(req.getEmail());

    return ResponseEntity.ok(order);
}

Hậu quả: Không thể tái sử dụng logic, không thể test độc lập, không có transaction boundary, controller phình to theo cấp số nhân.

✅ Đúng chuẩn: Controller mỏng — Service dày

OrderController.java — ĐÚNG 
@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public OrderResponse create(@RequestBody @Valid CreateOrderRequest request) {
        // ✅ Controller chỉ làm 1 việc: chuyển tiếp cho Service
        return orderService.createOrder(request);
    }
}
✅
Quy tắc ngón tay cái: Nếu trong Controller xuất hiện một khối if liên quan đến nghiệp vụ → đó là dấu hiệu logic đang đặt sai chỗ.

5 @Service & Dependency Injection

Annotation @Service đánh dấu một class là Spring Bean thuộc tầng nghiệp vụ. Về mặt kỹ thuật nó tương đương @Component, nhưng mang ngữ nghĩa rõ ràng giúp code dễ đọc và hỗ trợ AOP pointcut.

Cách inject dependency — nên chọn cách nào?

OrderService.java 
@Service
@RequiredArgsConstructor   // Lombok tự sinh constructor cho các field final
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
    private final VoucherService voucherService;

    // Constructor injection → field có thể là final (immutable)
    // → dễ test, không cần Spring context, không bị NullPointerException
}
OrderService.java — KHÔNG khuyến nghị 
@Service
public class OrderService {

    @Autowired   // ❌ Field injection
    private OrderRepository orderRepository;

    // Nhược điểm:
    // 1. Không dùng được 'final' → field có thể bị gán lại
    // 2. Không thể khởi tạo object bằng 'new' trong unit test
    //    → bắt buộc phải dùng reflection hoặc Spring context
    // 3. Che giấu "quá nhiều dependency" (vi phạm SRP mà không ai thấy)
    // 4. Gây lỗi vòng lặp phụ thuộc khó phát hiện
}
OrderService.java 
@Service
public class OrderService {

    private OrderRepository orderRepository;

    @Autowired
    public void setOrderRepository(OrderRepository repo) {
        this.orderRepository = repo;
    }

    // Dùng khi dependency là optional hoặc cần thay đổi lúc runtime.
    // Với hầu hết trường hợp → ưu tiên constructor injection.
}
💡
Vì sao Constructor Injection là lựa chọn số 1?
  • Cho phép khai báo field final → an toàn đa luồng.
  • Unit test chỉ cần new OrderService(mockRepo, ...), không cần Spring.
  • Nếu constructor có quá nhiều tham số → "mùi" cho thấy class đang vi phạm SRP.

6 Transaction Management với @Transactional

Service Layer chính là nơi đặt @Transactional — vì đây là tầng hiểu được một đơn vị công việc (unit of work) gồm nhiều thao tác DB phải thực hiện "tất cả hoặc không gì cả".

OrderService.java 
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;

    @Transactional   // ← Toàn bộ method là MỘT transaction
    public OrderResponse createOrder(CreateOrderRequest request) {
        // Nếu bất kỳ bước nào ném exception → rollback toàn bộ
        Order order = new Order();
        orderRepository.save(order);

        // Trừ kho
        productRepository.decreaseStock(request.productId(), request.quantity());

        return mapper.toResponse(order);
    }

    @Transactional(readOnly = true)   // ← Tối ưu cho thao tác đọc
    public OrderResponse getOrder(Long id) {
        return orderRepository.findById(id)
                .map(mapper::toResponse)
                .orElseThrow(() -> new ResourceNotFoundException("Order", id));
    }
}

Các thuộc tính quan trọng

Thuộc tínhMặc địnhÝ nghĩa
propagationREQUIREDDùng transaction hiện có, nếu chưa có thì tạo mới
isolationDEFAULTMức cô lập giữa các transaction đồng thời
readOnlyfalseBật true cho query → Hibernate bỏ dirty-checking, nhanh hơn
rollbackForRuntimeExceptionChỉ định thêm exception checked cũng rollback
timeout-1Giới hạn thời gian (giây) trước khi rollback

🚨 Cạm bẫy kinh điển: Self-Invocation

Spring AOP dùng proxy để bọc transaction. Khi bạn gọi một method @Transactional từ chính class đó, lời gọi không đi qua proxy → @Transactional hoàn toàn bị bỏ qua.

❌ SAI — không có transaction 
@Service
public class OrderService {

    public void placeOrder(Order o) {
        this.saveInternal(o);   // ❌ self-invocation
    }

    @Transactional
    public void saveInternal(Order o) {
        orderRepository.save(o); // KHÔNG có transaction!
    }
}
✅ ĐÚNG 
@Service
public class OrderService {

    @Transactional  // đặt ở method public được gọi từ BÊN NGOÀI
    public void placeOrder(Order o) {
        orderRepository.save(o);
        // mọi thao tác DB trong đây cùng 1 transaction
    }
}
🚨
Lưu ý: @Transactional chỉ hoạt động trên public method và khi được gọi từ bean khác (qua proxy). Method private, final hoặc gọi nội bộ trong cùng class đều không có tác dụng.

7 Ví dụ thực chiến: Module Đặt hàng

Chúng ta sẽ xây dựng hoàn chỉnh luồng đặt hàng theo kiến trúc chuẩn. Nhấn vào từng tab để xem code.

Order.java 
@Entity
@Table(name = "orders")
@Getter @Setter
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private Long customerId;
    private BigDecimal totalAmount;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {
        item.setOrder(this);
        this.items.add(item);
    }
}

OrderService.java — ⭐ TRÁI TIM CỦA BÀI HỌC 
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
    private final VoucherService voucherService;
    private final OrderMapper orderMapper;

    @Transactional
    public OrderResponse createOrder(CreateOrderRequest request) {
        log.info("Tạo đơn hàng cho customer={}", request.customerId());

        // ── Bước 1: Validate nghiệp vụ ────────────────────────────
        if (request.items() == null || request.items().isEmpty()) {
            throw new BusinessException("Đơn hàng phải có ít nhất 1 sản phẩm");
        }

        // ── Bước 2: Kiểm tra tồn kho & tính tiền ──────────────────
        BigDecimal total = BigDecimal.ZERO;
        List<OrderItem> items = new ArrayList<>();

        for (OrderItemRequest itemReq : request.items()) {
            Product product = productRepository.findById(itemReq.productId())
                    .orElseThrow(() ->
                        new ResourceNotFoundException("Sản phẩm", itemReq.productId()));

            if (product.getStock() < itemReq.quantity()) {
                throw new BusinessException(
                    "Sản phẩm '" + product.getName() + "' chỉ còn "
                    + product.getStock() + " trong kho");
            }

            // Trừ kho ngay trong transaction
            product.setStock(product.getStock() - itemReq.quantity());

            OrderItem item = new OrderItem(product, itemReq.quantity(), product.getPrice());
            items.add(item);
            total = total.add(item.getSubtotal());
        }

        // ── Bước 3: Áp voucher ────────────────────────────────────
        if (StringUtils.hasText(request.voucherCode())) {
            total = voucherService.applyDiscount(request.voucherCode(), total);
        }

        // ── Bước 4: Tạo & lưu đơn hàng ────────────────────────────
        Order order = new Order();
        order.setCustomerId(request.customerId());
        order.setTotalAmount(total);
        order.setStatus(OrderStatus.PENDING);
        items.forEach(order::addItem);

        Order saved = orderRepository.save(order);
        log.info("Đã tạo đơn hàng id={}, total={}", saved.getId(), total);

        return orderMapper.toResponse(saved);
    }

    @Transactional(readOnly = true)
    public List<OrderResponse> getOrdersByCustomer(Long customerId) {
        return orderRepository.findByCustomerId(customerId)
                .stream()
                .map(orderMapper::toResponse)
                .toList();
    }
}

    @PostMapping

Phân tích: Toàn bộ nghiệp vụ (validate, kiểm kho, tính tiền, áp voucher, tạo đơn) nằm gọn trong createOrder(). Nếu bất kỳ bước nào ném exception, @Transactional sẽ rollback cả việc trừ kho lẫn việc tạo đơn → dữ liệu luôn nhất quán.

8 Xử lý ngoại lệ trong Service Layer

Service nên ném ra exception nghiệp vụ (business exception) thay vì trả về null hay boolean — để tầng trên biết chính xác điều gì sai.

Exception & Global Handler 
// ── 1. Exception nghiệp vụ ────────────────────────────────
public class BusinessException extends RuntimeException {
    public BusinessException(String message) {
        super(message);
    }
}

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String resource, Object id) {
        super(resource + " không tồn tại với id = " + id);
    }
}

// ── 2. Bắt tập trung tại tầng API ─────────────────────────
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException ex) {
        log.warn("Vi phạm nghiệp vụ: {}", ex.getMessage());
        return ResponseEntity.badRequest()
                .body(new ErrorResponse("BUSINESS_ERROR", ex.getMessage()));
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse("NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
        String msg = ex.getBindingResult().getFieldErrors().stream()
                .map(e -> e.getField() + ": " + e.getDefaultMessage())
                .collect(Collectors.joining(", "));
        return ResponseEntity.badRequest()
                .body(new ErrorResponse("VALIDATION_ERROR", msg));
    }
}
⚠️
Nguyên tắc: Service không nên import ResponseEntity hay bất kỳ thứ gì thuộc tầng web. Hãy để Service ném exception "thuần khiết", còn việc chuyển thành HTTP status là trách nhiệm của tầng Controller/Advice.

9 Testing Service Layer

Service Layer là nơi dễ và nên được unit test nhất, vì nó không phụ thuộc vào HTTP hay database thật (nhờ Mockito).

OrderServiceTest.java 
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock OrderRepository orderRepository;
    @Mock ProductRepository productRepository;
    @Mock VoucherService voucherService;
    @Mock OrderMapper orderMapper;

    @InjectMocks OrderService orderService;

    @Test
    @DisplayName("Phải ném BusinessException khi sản phẩm không đủ tồn kho")
    void shouldThrowWhenOutOfStock() {
        // ── Given ──────────────────────────────────────────────
        Product product = new Product();
        product.setId(1L);
        product.setName("iPhone 15");
        product.setStock(2);
        when(productRepository.findById(1L)).thenReturn(Optional.of(product));

        CreateOrderRequest request = new CreateOrderRequest(
                10L,
                List.of(new OrderItemRequest(1L, 5)),   // đặt 5 > tồn 2
                null
        );

        // ── When / Then ────────────────────────────────────────
        BusinessException ex = assertThrows(
                BusinessException.class,
                () -> orderService.createOrder(request)
        );
        assertThat(ex.getMessage()).contains("chỉ còn 2");

        // Đảm bảo KHÔNG có đơn nào được lưu
        verify(orderRepository, never()).save(any());
    }

    @Test
    @DisplayName("Tạo đơn hàng thành công với tổng tiền đúng")
    void shouldCreateOrderSuccessfully() {
        Product p = new Product();
        p.setId(1L);
        p.setPrice(new BigDecimal("1000000"));
        p.setStock(10);
        when(productRepository.findById(1L)).thenReturn(Optional.of(p));
        when(orderRepository.save(any())).thenAnswer(inv -> inv.getArgument(0));

        var req = new CreateOrderRequest(10L, List.of(new OrderItemRequest(1L, 2)), null);
        orderService.createOrder(req);

        ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
        verify(orderRepository).save(captor.capture());

        assertThat(captor.getValue().getTotalAmount())
                .isEqualByComparingTo("2000000");
    }
}
🧪
Kim tự tháp kiểm thử: Unit Test (Service + Mockito) nên chiếm ~70% tổng số test. Integration Test (dùng @SpringBootTest + Testcontainers) chiếm ~20%. E2E chỉ ~10%.

10 Best Practices & Anti-patterns

✅ Nên làm

  • Đặt toàn bộ business logic trong Service, không rải rác ở Controller hay Entity.
  • Dùng constructor injection với field final.
  • Đặt @Transactional ở method public của Service, dùng readOnly = true cho query.
  • Trả về DTO, không trả Entity thô ra ngoài (tránh lộ cấu trúc DB, tránh vòng lặp JSON).
  • Ném exception nghiệp vụ rõ ràng, message thân thiện với người dùng.
  • Giữ mỗi Service method ngắn gọn, một nhiệm vụ; tách nhỏ khi vượt quá ~30 dòng.
  • Log những sự kiện quan trọng: bắt đầu/kết thúc xử lý, lỗi nghiệp vụ.
  • Đặt tên method theo ngôn ngữ nghiệp vụ: placeOrder, cancelOrder, applyVoucher.

❌ Tránh mắc phải

  • Fat Controller: nhồi nghiệp vụ vào Controller như ví dụ ở mục 4.
  • Gọi Repository trực tiếp từ Controller — phá vỡ kiến trúc phân lớp.
  • Service gọi Service lẫn nhau tạo vòng lặp (circular dependency) → dấu hiệu chia tách module chưa tốt.
  • Self-invocation với @Transactional — transaction không có hiệu lực.
  • Trả về Entity từ Service → lazy-loading exception, lộ dữ liệu nhạy cảm.
  • Nuốt exception bằng catch (Exception e) { } rỗng.
  • Anemic Domain Model: Entity chỉ có getter/setter, mọi logic dồn hết vào Service khổng lồ.
  • God Service: một class OrderService 2000 dòng làm mọi thứ → hãy tách thành OrderCreationService, OrderQueryService, OrderCancellationService…
🔥
Cảnh báo God Service: Khi một Service có hơn 10 dependency được inject, đó là tín hiệu rõ ràng class đang vi phạm nguyên lý Single Responsibility và cần được chia nhỏ.

12 Tổng kết

🧩

Service = Bộ não

Nơi hội tụ mọi quy tắc nghiệp vụ, điều phối dữ liệu từ nhiều nguồn và quyết định kết quả cuối cùng.

🛡️

Transaction Boundary

Service là nơi xác định "đơn vị công việc" — tất cả thành công hoặc rollback toàn bộ.

🎯

Trách nhiệm đơn nhất

Controller mỏng — Service dày — Repository thuần truy vấn. Đừng trộn lẫn ba vai trò.

🧪

Dễ kiểm thử

Với Mockito, Service có thể test độc lập, không cần database hay HTTP server.
